# CivicFix AI

CivicFix AI helps citizens report civic infrastructure problems — potholes, blocked drains, visible water
pipeline leaks, damaged traffic signals, garbage accumulation, damaged footpaths and similar publicly
maintained assets — and helps authorities review an AI-assisted assessment of each report.

A citizen uploads a photograph and a location. An AI service returns a structured assessment: what the
issue appears to be, how severe it looks, how confident the model is, what is visibly wrong, which safety
concerns exist, which department usually handles it, what a repair would involve, and which details are
still missing before work can be planned.

## Repository layout

```
civicfix-ai/
├── frontend/     # React + Vite application (this developer's work) — see frontend/README.md

└── .gitignore
```

### Where is `backend/`?

`backend/` is owned by a **different developer, working on a different laptop**, and it is intentionally
not present yet. It will contain the Python/FastAPI service that performs the AI inference and exposes the
HTTP API consumed by the frontend.

Nothing has been created inside `backend/` from the frontend side, and no placeholder backend files exist
so that the directory looks populated. Git cannot track an empty directory, so `backend/` will appear in
this repository the moment its owner pushes its first file — and it will keep working independently of
`frontend/`.

---

## Independent development

The two halves of the project are developed separately and joined only through an HTTP contract:

- **Frontend** — React, Vite, JavaScript, Tailwind CSS. Runs on its own, with no backend required for
  development or review.
- **Backend** — Python, FastAPI, AI inference. Owns the model, the database and all privileged secrets.

Rules that keep the merge surface small:

1. All frontend application code, dependencies and configuration live under `frontend/`.
2. All backend code lives under `backend/`.
3. There are no shared config files at the root beyond this README and a `.gitignore` that ignores
   build output, dependencies, editor files and local `.env` files. Backend-specific ignores belong in
   `backend/.gitignore`, owned by the backend developer.
4. Each side keeps its own dependency manifest and lockfile.
5. The only coupling is the HTTP contract described below.

Neither application changes how the other is built, installed or run.

## Running the frontend

```bash
cd frontend
npm install
npm run dev          # http://localhost:5173
```

Optional configuration: copy `frontend/.env.example` to `frontend/.env.local` and set `VITE_API_URL` to
the backend base URL (defaults to `http://localhost:8000`). Full details — including production builds and
Vercel deployment — are in [`frontend/README.md`](frontend/README.md).

## Running the backend (once it lands)

The backend developer documents this under `backend/`. It is expected to expose the API over HTTP on
`http://localhost:8000` for local development, and to allow CORS from the frontend origin
(`http://localhost:5173` in development).

## The integration contract

The frontend is wired to the following endpoint and is already able to render a real response from it.

### Request

```
POST /analyze
Content-Type: multipart/form-data
```

| Field                | Type   | Required | Notes                                                   |
| -------------------- | ------ | -------- | ------------------------------------------------------- |
| `file`               | File   | yes      | JPEG, PNG or WEBP, maximum 8 MB (validated in the browser). |
| `location`           | string | yes      | Free-text location supplied by the citizen.              |
| `additional_details` | string | no       | Optional context; sent as an empty string when unused.   |

The frontend never sets `Content-Type` manually for this request, so the multipart boundary is generated by
the browser.

### Illustrative response

```json
{
  "issue_type": "Pothole",
  "is_civic_issue": true,
  "confidence": 0.95,
  "severity": "High",
  "description": "Visible road surface damage",
  "observations": ["Visible surface depression"],
  "safety_concerns": ["Potential hazard to road users"],
  "suggested_department": "Road maintenance",
  "recommended_actions": ["Inspect the damaged section"],
  "resources": [
    { "item": "Road repair materials", "purpose": "Potential repair resource, subject to inspection" }
  ],
  "estimated_cost_inr": {
    "minimum": null,
    "maximum": null,
    "basis": "Insufficient information for a reliable estimate"
  },
  "estimated_duration_hours": {
    "minimum": null,
    "maximum": null,
    "basis": "Further assessment required"
  },
  "needs_site_inspection": true,
  "missing_information": ["Measured damage dimensions"],
  "location": "Pune",
  "estimate_status": "preliminary",
  "authority_status": "not_submitted"
}
```

This is an illustrative contract, not a guarantee. Every field is optional as far as the frontend is
concerned: missing or `null` values are reported as "not reported" in the interface, never invented, and
null cost or duration is never displayed as zero. Unknown severity values are shown with their original
text, and unexpected fields are listed in a response-completeness note so schema drift is obvious.

If the schema changes, update `frontend/src/lib/analysis.js` (normalisation) and
`frontend/src/services/civicfixApi.js` (request shape); the presentation components read only the
normalised object.

### Analysis is not storage

`POST /analyze` produces an assessment. It does **not** save a report unless the backend says so, and it
does **not** submit anything to a government authority. Report persistence, report history, jurisdiction
routing, authority submission, mapping and authentication are separate capabilities that remain
placeholders on the frontend until the backend exposes them.

## Environment and security

- Frontend configuration uses `VITE_`-prefixed variables, which Vite inlines into the browser bundle and
  are therefore **public**. Only the backend base URL belongs there.
- The Groq API key, database URLs, service-role keys and any other privileged secret belong exclusively to
  the backend environment. They must never appear in `frontend/`, in a `VITE_` variable, or in source
  control.
- Real `.env` files are git-ignored on both sides; `.env.example` files document the expected variables.
- CORS is configured on the backend. The frontend does not proxy around it.
